# Архитектура и план развития

## Цель

Windows-приложение, позволяющее записывать личные и онлайн-встречи, распознавать речь локально, превращать диалог в проверяемые знания и задачи, находить связанные сведения и готовить инструкции.

## Состав 0.1

- **PySide6 / Qt Widgets**: нативные окна, выбор устройств, таблицы, системный трей, QGraphicsView для карты. Нет Chromium/Electron/WebView.
- **PyAudioWPatch / WASAPI**: два независимых QThread для микрофона и loopback. 16-bit PCM в частоте устройства; уровень RMS в диапазоне −60…0 dBFS отображается шкалой.
- **Дисковая очередь**: закрытые WAV-фрагменты регистрируются в SQLite. Память не растёт пропорционально длительности записи. При ошибке сохраняется причина и возможен повтор.
- **faster-whisper / CTranslate2**: один worker, модель из локальной папки, VAD, CPU int8 / CUDA int8_float16. Downmix и полифазная передискретизация до 16 kHz.
- **Ollama / Qwen3**: только localhost, структурированный JSON, проверка Pydantic и точного вхождения цитат. Нет выполнения кода, shell-команд или действий из содержимого диалога.
- **SQLite WAL + FTS5**: отдельное соединение на операцию, транзакции, внешние ключи, индексы очереди/напоминаний/встреч. FTS обновляется триггерами при редактировании.

## Модель данных

| Сущность | Ключи и связи | Назначение |
|---|---|---|
| meetings | id | Название, UTC дата создания |
| chunks | id, meeting_id, unique path | Источник, сдвиг, длительность, pending/done/error |
| segments | id, meeting_id, chunk_id | Время, источник, оригинал и исправленный текст |
| reports | id, meeting_id, fingerprint | Версии JSON-протокола и отпечаток исходных реплик |
| tasks | id, meeting_id, source_id, dedup | Поручение, контекст, цитата, исполнитель, UTC срок/напоминание |
| corrections | id, segment_id | История ручных изменений |
| terms | wrong | Подтверждённые замены терминов |
| shots | id, meeting_id | PNG, подпись, время снимка |
| documents / search_fts | kind + ref_id | Поисковая проекция актуальных данных |

## Жизненный цикл

1. Запись начинается только по нажатию пользователя, с явно выбранными источниками.
2. Каждый источник пишет короткие WAV-файлы. После закрытия файла создаётся запись очереди. Служебный JSON позволяет восстановить регистрацию после сбоя.
3. Worker последовательно распознаёт доступные файлы. Запись реплик и состояние `done` фиксируются одной транзакцией; повтор не создаёт дубликатов.
4. После завершения очереди пользователь запускает протокол. Модель речи освобождается перед запуском LLM, чтобы снизить совместное потребление RAM/VRAM.
5. Все части диалога анализируются. Протокол фиксируется только после успеха каждой части; выдуманная цитата вызывает ошибку, а не молчаливое сохранение.
6. Задачи создаются черновиками. Срок в речи сохраняется в протоколе текстом; даты и напоминания задаёт пользователь, без угадывания относительных сроков.
7. Исправление текста обновляет FTS. Отпечаток позволяет показать, что существующий протокол устарел. Старые версии сохраняются.
8. Карта объединяет точные названия групп/тем и хранит связи с репликой и встречей. При изменении исходника ранее выведенные знания требуют повторного анализа.

## Уровни доверия и точность

Проверка цитаты доказывает её наличие в реплике; она не доказывает корректность трактовки. Ответственного, действие и контекст надо сверять. Никакие сообщения людям, приглашения, действия в чужих системах или запускаемые скрипты модель самостоятельно не выполняет.

Источник «Система» не означает конкретного человека. Несколько участников внутри системного аудио пока не разделяются. Раздельные источники имеют метки начала на общей monotonic-шкале; компенсация рассинхронизации часов устройств и акустическое эхоподавление пока не реализованы.

## Измерения на ПК пользователя

Собрать CPU, RAM/свободную RAM, GPU/VRAM, ОС, устройство аудио. Провести 10 минут для одного источника и 10 минут для двух. Измерить средний/P95 RTF, задержку текста, размер очереди, максимальную RAM, пропуски и повторы. При необходимости перейти с `small` на `base`, CPU на проверенную CUDA или отключить генерацию во время записи. Протоколы создаются после записи.

## Реализовано в 0.2

Дополнительный backend `EmbeddedLLM` использует локальный Qwen2.5 Instruct GGUF через llama-cpp-python. Он не создаёт HTTP-клиент; общий контракт схемы и проверки цитат сохраняется. Модель загружается в рабочем потоке и освобождается после анализа. Ollama остаётся доступным вариантом.

Схема SQLite v2 добавляет сроки удаления и отметки очистки в chunks, tombstones удалённых задач, ручные map_notes с FTS и направленные map_links. Связи ручных записей редактируются независимо от группировки протоколов; удаление заметки каскадно убирает только её связи. Кнопка «Достроить» создаёт заметку и направленную связь.

После успешного протокола обработанные фрагменты получают срок now+1h. Обслуживание проверяет срок раз в минуту, только для зарегистрированных WAV в каталоге встречи. Необработанная очередь, активные записи и внешние пути защищены. Ошибка удаления сохраняется для повторной попытки.

Обновления: GitHub commit → release.json → ZIP закреплённого коммита → проверка SHA-256 → ожидание RuntimeGuard → копия предыдущих исходников → замена только перечисленных файлов → pip. Ошибка во время замены или pip восстанавливает исходники. Сетевую проверку запускает пользователь. Обновляющий процесс использует базовый Python и стандартную библиотеку, чтобы GUI и его DLL успели закрыться. При выключении питания во время замены может понадобиться ручное восстановление из update-backups; это не транзакция файловой системы. База и модели не включены в манифест.
